## 0. 本文的定位与维护规则

### 0.1 三份文档的分工（重要）

| 文档 | 回答的问题 | 变更频率 | 谁写 |

3. 本文每轮大关账复核一次；若与代码冲突，**以代码和门禁输出为准**，并当场改本文。

## 2. 运行时分层与依赖规则

### 2.1 分层

| 层 | 位置 | 允许依赖 | 禁止依赖 |
|---|---|---|---|
| L0 数据/纯逻辑 | `Scripts/Core/**`、`Scripts/Economy/**` | 只能互相依赖 + .NET BCL | **禁止 `using UnityEngine`**（`SaveRepository` 注释明写"storage has no Unity dependency"） |
| L1 系统服务 | `Scripts/Combat/**`、`Scripts/Network/**` | L0 | 禁止引用 Presentation |
| L2 表现/UI | `Scripts/Presentation/**`、`Scripts/UI/**` | L0/L1 + UnityEngine | 页面之间不得直接互相调用，统一走 `FrontEndController` |
| L3 取证夹具 | `Assets/Editor/**` | 全部 | 仅 Editor 编译期；**不得被生产代码引用** |
| L4 管线 | `Tools/**` | 文件系统 | 不得依赖 Unity 运行时 |

### 2.2 现实与规则的偏差（需要在本文登记）

- **L0 的纯净度目前成立但无门禁保护**。`Tools/UnityCompileChecks` 只证明能编译，不证明"Core 里没有 UnityEngine"。
  建议加一条 5 行门禁：`grep -L` 遍历 `Core/**`、`Economy/**` 断言无 `using UnityEngine`。见任务书 T-06。
- **表现层与夹具的边界被"测试钩子"打穿**：生产类里直接放着 `...ForCheck` 方法
  （`FrontEndTrade` 25 处、`WorldPropLayer` 13 处、`FrontEndCombat` 11 处、`PuppetActor` 10 处、`FrontEndWorld` 7 处）。
  这带来两个真实成本：① 生产构建里带着永不调用的取证代码；② 夹具改动会污染生产文件的历史。
  建议逐步把 `*ForCheck` 收进 `#if UNITY_EDITOR` 或同类的 `partial` 取证文件。见任务书 T-07。

## 3. 客户端启动与页面路由

### 3.1 启动顺序（`FrontEndController.Awake`）

1. 建 MainCamera（正交、纯色背景）、设 `targetFrameRate = 60`。
2. 从 `Resources/Fonts/` 加载两套字体并**动态建 TMP 图集**（`NotoSerifCJKsc-Regular` 正文、
   `ZhiMangXing-Regular` 书法）。缺任一个直接抛异常——**这是有意为之的硬失败**，避免全屏豆腐块。
3. `UiKit` 初始化；建 Canvas（`ScreenSpaceOverlay`，参考分辨率 1920×1080，`Expand` 适配）。
4. `BuildBackdrop()`：`Art/menu-painting` 主视觉 + 墨色底 + 左侧渐变纱罩 + `MenuAmbience`。
5. 订阅两个事件：`NpcArrived → TalkTo(id)`、`EncounterArrived → ShowCombat(id)`。
   这两个事件是 Core 与表现层之间**唯一**的"世界交互回传"通道（历史 T021：订阅了却没人 raise）。
6. 加载 3 套 `CharacterPreset`（`Resources/Characters/*.asset`），数量不为 3 直接抛异常。
7. 建 `SaveRepository`：存档根目录 = `TWELVEJADE_SAVEDIR`（验收隔离）或
   `Application.persistentDataPath/Saves`。注入 `Table`（物品表）供校验使用。
8. `LoadSettings()` → `ShowMenu()`。

### 3.2 页面路由（"page" 字符串状态机）

| page | 入口 | 职责文件 | 备注 |
|---|---|---|---|
| `menu` | `ShowMenu()` | FrontEndController | 启程/续缘/行迹/设置/制作信息/离去 |
| `slots` | `ShowSlots(bool creating)` | FrontEndCharacters | 三槽位，新建或读取 |
| `character-creation` | `ShowCharacterCreation(slot)` | FrontEndCharacters | 出身/性别/面容/命格重掷 + `FateDialogue` |
| `preview` | `ShowPreview(data)` | FrontEndCharacters | 三视图 / 六种动作（数字键 1–6） |
| `town` | `ShowTown()` | FrontEndWorld | 世界页：分块地形、主角纸偶、NPC、遭遇点、寻路 |
| `trade` | `ShowTrade(merchantId, black)` | FrontEndTrade | 货架、议价、黑市、记忆回响、摸骨相面 |
| `combat` | `ShowCombat(encounterId)` | FrontEndCombat | 部位打击、看破闪避、服药、磨刃、战利品 |
| `settings` / `credits` | `ShowSettings()` / `ShowCredits()` | FrontEndSettings | — |

> 页面切换统一走 `BeginPage(name)`：销毁旧 `content`、重建、做 0.22s 淡入（`reduceMotion` 时跳过）。
> 键盘：`Esc` 逐层回退（行囊 → 模态 → 交易/战斗 → 菜单 → 退出请求），`B` 在城镇页开行囊。

### 3.3 架构评价

- **优点**：`FrontEndController` 是 `partial class`，把 UI 按页面拆成 9 个文件，比单文件好读；
  `UiKit` 把布局原语（Panel/Label/Button/Art/Slider）收口，几何尺寸集中，避免样式散落。
- **风险**：9 个分部合起来仍是**一个 ~5,800 行的 God Class**，`page` 用字符串而非枚举，页面间共享字段（`bagOverlay`、
  `modal`、`activeSave`）散布在不同文件里，`ForCheck` 钩子与生产逻辑同处一室。规模再长一个阶段前，**必须**做一次
  拆分（建议：把每个页面升级为独立 MonoBehaviour，`FrontEndController` 只保留路由 + 共享上下文）。
  见任务书 T-07。

```text
        ▼

        │                                     + props/npcs/encounters/landmarks/acceptance)
        │  Tools/compose-world-chunks.py
        ▼
Assets/Resources/Art/World/Chunks/chunk_{x}_{y}.png  (64 块：正式材质产物)

        │  回落（未配 chunkArtTemplate 时）

```

**材质链**（`world-material-gen.json` → 单张材质）：

```text
make-procedural-base.py  /  make-ai-overlay.py  /  make-tileable-texture.py
        ▼
compose-final-material.py   → make-world-materials.py 门禁（seam + 内容探针 + finalPass）
        ▼
Assets/ArtSource/world/…（源）  →  Resources/Art/World/Chunks（产物）
```

### 4.2 运行期如何用

- `TownMap.ChunkArtAt(col,row)`：**配了 `chunkArtTemplate` 就走模板**（正式产物），否则回落 `chunks[].art`（灰盒）。
- `FrontEndWorld.BuildWorldChunks()` 每块建一个 `RawImage`；**缺图不静默**——`LogError` + 品红块 + 顶部通知。
  这是好设计（"没接上"与"世界就长这样"必须可区分）。
- `TownMap.Blocked` 是**轴对齐矩形**集合（山体/河面），`CanStand()` 走 `Walkable.Contains && !Blocked`。
  外部注入走 `RegisterBlocker(source, rect)` / `ClearBlockers(source)`（ADR-033 同形状原则，防止校验器与运行期不同形）。
- `acceptance` 节点把验收阈值（`minWorldWidthToViewportRatio` 等）配置化，不再硬编码进 `WorldChecks`。

### 4.3 已知真源风险

| 风险 | 证据 | 建议 |
|---|---|---|
| **双艺术源并存，读者会被误导** | `chunkArtTemplate`（正式）与 `chunks[].art`（灰盒）+ `phase:"world-greybox"` 同时存在；M 的 Q1.7 报告据此误判"plaza.png 根本没在屏幕上" | 正式产物稳定后，把 `chunks[].art` 与 `phase` 一次性清理成单一语义；或在字段上加注释 + 门禁断言二者不冲突 |
| **`town-map.json` 手工回填会丢** | bridges 曾手工回填，`sync --write` 会冲掉（状态板明写） | 任何人不得手改 `town-map.json`；只改 `make-world-greybox.py` 再同步。已成立，保持 |
| **`columns/rows` 曾是死白名单** | T020（已 CLOSED） | 保留教训：白名单项必须与生成器实际产出对齐 |
| **两个近 2MB JSON 进 Resources** | 1.97MB + 2.12MB，且是"生成物 + 派生物"两份 | 评估运行期内存/加载耗时；长期考虑把 `town-world-gen.json` 移出 Resources（它是构建期输入，不是运行期需要） |
| **`phase` 字段语义漂移** | 注释说 `terrain`/`full`，实际值是 `world-greybox` | 明确枚举并加门禁校验 |

## 6. 存档架构（Schema 11）

### 6.1 落盘位置与文件

| 项 | 值 |
|---|---|
| 根目录 | `Application.persistentDataPath/Saves`（验收用 `TWELVEJADE_SAVEDIR` 覆盖） |
| 槽位文件 | `slot-1.json` / `slot-2.json` / `slot-3.json`（`SaveRepository.SlotCount = 3`） |
| 备份 | `slot-N.json.bak`（主档损坏时回落，`SlotState.Recovered`） |
| 设置文件 | 由 `SaveRepository.LoadSettings/SaveSettings` 管理（另有 `SettingsLoadState` 三态恢复） |
| 编码 | UTF-8；外部校验 `IsValid()` 拒收，`.bak` 兜底，绝不做"静默修好" |

### 6.2 `SaveData` 字段（schemaVersion = 11，客户端与服务端同批）

| 字段 | 引入版本 | 含义 | 校验 |
|---|---|---|---|
| `schemaVersion` | 1 | 存档版本，缺失即 Corrupt | `1..CurrentSchemaVersion` |
| `slot` | 1 | 槽位 | 必须与文件名一致 |
| `characterId` / `characterName` | 1 | 角色标识 / 姓名 | 非空，姓名 ≤ 16 字符 |
| `createdUtc` / `updatedUtc` | 1 | 创建/更新（`DateTimeOffset`，带偏移） | `TryParse` |
| `location` | 1 | 当前场景 | 必须 `"CharacterPreview"` |
| `facing` | 1 | 朝向 0–3 | 范围 |
| `gender` / `faceStyle` / `traits` / `destiny` | 2 | 人物刻画（投胎问命） | 枚举 / 0–1 / ≤ TraitsPerCharacter / ≤ 32 字符 |
| `coins` / `localReputation` / `bag` | 3 | 铜钱 / 声望 / 行囊 | 0–9,999,999 / 0–100 / 按物品表堆叠上限 |
| `merchants` | 4 | 商人存货与交易次数 | id 非空 |
| `oneTimeFlags` | 5 | 一次性事件标记 | ≤ 32 条、非空、去重 |
| `quests` | 6 | 任务进度 | id 非空 |
| `worldDay` / `worldMinuteOfDay` | 7 | 世界时间（**存整数，不存时间戳**） | 世界时间范围内 |
| `npcs` | 8 | NPC 关系/记忆/目标 | id 非空；**不按表裁剪** |
| `clues` | 9 | 线索账本 | id 非空；**不按表裁剪** |
| `dialogue` | 9 | 当前对话断点 | 两端都空则视为无 |
| `chapter` | 10 | 章进度（走到第几段 / 已结算集合） | 结构自洽 |
| `karmaEvents` | 10* | 气运善行簿（17 善事 + 8 奇遇的沉淀） | **校验从 v10 起生效**（字段是 10 期间纯增量加上的） |
| `gear` | 11 | 装备槽 + 耐久（T051） | 槽合法、同槽唯一、耐久 ≥ 0 |
| `crafts` | 11 | 每道方子的制作次数（T046 熟练度） | id 非空、次数 > 0、同 id 唯一 |
| `bagClipped` | — | `[NonSerialized]` 瞬态：行囊是否已规整，**不进 JSON** | — |

### 6.3 两条必须记住的设计原则（已被反复验证）

1. **能算出来的不进存档**：存"第几天 + 当天第几分钟"而不存时间戳（不依赖机器时区）；
   存"制作次数"而不存"熟练度等级"（等级是次数的函数）；装备只存"穿哪件 + 剩多少耐久"，属性由 `CombatGear` 实算。
2. **迁移只补缺、不覆盖；可反复调用**：`SaveData.Migrate()` 对每个字段都只做"补空 + 归一化 + 去重"，
   绝不按版本清空。且**读档才 Normalize，写档不 Normalize**——否则越界堆叠会被悄悄截到上限，脏档再也拒不掉。

### 6.4 跨端契约（**最高危的单点**）

```
客户端 SaveData.CurrentSchemaVersion = 11
服务端 ClientSchema.SUPPORTED_SCHEMA = 11
```

- 服务端 `SaveController` 对 `schemaVersion > SUPPORTED_SCHEMA` 返回 `40901`；低于则收下并标 `migratable=true`。
- **两侧必须同批改**（`ClientSchema.java` 的 Javadoc 原话："先改一侧是'先上一半'的交付，不是安全的一半"）。
- 存档上限 **256KB**：客户端 `network-config.json.maxPayloadBytes = 262144`、服务端应用层先量再存、
  Tomcat form 上限同步 262144。三处口径一致。
- **容量预算仍未实测**（W4-A 在办）：schema 继续加字段前必须先有实测余量，否则会把"上传失败"变成玩家可感知的故障。

### 6.5 架构评价

- 单文档存档（角色+行囊+任务+NPC+线索+气运+装备全在一个根对象里）在**这个规模**是对的：一次读写、一次迁移、一次校验。
- 但它的代价是**所有系统必须锁步升版**，且服务端只"存不读"不能做服务端迁移。
  当 schema 逼近 256KB 或要加"多存档云同步"时，建议评估：
  ①把低频大对象拆成独立子树（如 `karma`/`crafts`）；②或加一个 `ext{}` 自由袋给实验性字段，避免每加一条就动根结构。
  **当前不建议动**——先拿 W4-A 的实测数据说话。

## 7. 网络与云存档

### 7.1 组件与职责

| 组件 | 职责 |
|---|---|
| `NetworkConfig` | 读 `network-config.json`：baseUrl / timeout / maxRetry / backoff / maxPayloadBytes |
| `NetworkClient` | 协程驱动 `SendJson`：重试（网络错/5xx，4xx 不重试）+ 退避（base×2^n）+ 401/40102 自动续期并重放一次 |
| `ITransport` / `UnityWebRequestTransport` | 传输抽象；夹具用 `ScriptedTransport`/`RecordingTransport` 假传输 |
| `AuthService` | register / login / refresh / changePassword / me / logout |
| `CloudSaveService` | list / upload / download / 冲突判定 / payload 预检 |
| `LocalCredentialManager` | token 与用户名持久化（`IKeyValueStore`，生产用 PlayerPrefs）；离线态/在线态切换 |
| `LocalBackupUtility` | 三槽位离线导出为 bundle（含 SHA-256） |
| `NetworkRuntime` | 探测 + 本地仓储工厂 |

### 7.2 时序（上传）

```text
UI → CloudSaveService.UploadSlot(slot)
       → PrecheckPayload(saveJson)   # > 256KB 直接 PayloadTooLargeException，不发请求
       → AuthService 确保有有效 token（必要时 refresh）
       → NetworkClient.SendJson(POST /api/save/upload, {slot, schemaVersion, save})
            ├─ 网络错/5xx → 退避重试（≤ maxRetry）
            ├─ 401 + 40102 → 续期一次 → 用新 token 重放
            └─ code==0 → 成功，记录 updatedAt
```

### 7.3 冲突判定（`CloudSaveService.Compare`）

- 本地 `updatedUtc` 是 `DateTimeOffset.UtcNow.ToString("O")`，**带偏移**。
- 云端 `updatedAt` 由服务端产生。**历史 T034**：服务端曾是 `LocalDateTime.now()` + `ISO_LOCAL_DATE_TIME`（**不带偏移**）。
  裸时间会被 `DateTimeOffset.TryParse` **静默补上本机时区**，于是"看起来对、换机房就错"。
  ⇒ 现口径：**云端时间不带显式偏移 ⇒ 判 `Unknown`，交人工对比**（`HasExplicitOffset` 守门 + `NetworkShot S14` 断言）。
  服务端改为带偏移 UTC 后客户端自动恢复方向判定（W4-K 在办）。

### 7.4 架构风险

| 风险 | 说明 | 建议 |
|---|---|---|
| **假传输依赖** | `NetworkShot` 十条场景全走假传输，真契约漂移只能靠人工 `curl`/`acceptance.ps1`（T035） | 加 `TWELVEJADE_LIVE=1` 的真后端冒烟；把"响应原文"固化成常量（部分已做 S11–S14） |
| **无服务端迁移** | 服务端"只存不读"；客户端升版而服务端只做版本闸 | 可接受；但要明确 40901 的用户文案与"客户端过旧"提示路径 |
| **离线优先的边界** | `LocalCredentialManager` 有 EnterOfflineLocal/SetOnline，但**"离线时做了什么、联网后怎么合并"没有单一文档** | 在本文补一张状态机（见任务书 T-06） |

### 8.2 关键约定

|---|---|
| 响应信封 | `{code, message, data}`；`code == 0` 成功；`data` 为 null 时字段整体不输出（`@JsonInclude(NON_NULL)` 只作用信封） |

- **真 MySQL 从未验证**（T024/T102）：类型/方言/时区差异可能在首次上真库时集中爆发。
  `verify-mysql.ps1` + `docker-compose.mysql.yml` 已备，缺的是**执行**。
- **H2 与 MySQL 的行为差异**（如并发唯一键冲突）会让"本地 66 绿"不代表"线上绿"。
- **`40903` 文案三处不一致**（服务端 message / 客户端文案 / API.md），已裁 D-55 由 W4-K 统一。

## 9. 玩法系统架构（Core / Economy / Combat）

### 9.1 共同模式：**静态账本类 + SaveData 作为唯一状态载体**

```text
QuestLedger / DialogueTree / NpcLedger / ClueLedger / KarmaTracker /
MerchantLedger / GearLedger / CraftLedger / ChapterLedger
        ↑ 全是 static 方法，输入 (SaveData, 表, 参数) → 就地改 SaveData
```

**优点**：无 DI、无生命周期、极易离线测试（`Tools/SaveChecks` 直接构造 `SaveData` 断言）。
**缺点**：没有接口、没有事件、没有依赖注入；系统之间的耦合全靠"都改同一个 `SaveData`"。
在这个规模是对的，但**每加一个系统，"谁能改 SaveData 的哪一段"就更难讲清楚**。
建议：在本文维护一张「SaveData 字段 ↔ 写入者」所有权表（见任务书 T-06）。

### 9.2 各系统要点

| 系统 | 核心类 | 真源 | 关键不变量 |
|---|---|---|---|
| 时间 | `WorldClock` / `WorldTime` | `worldDay`+`worldMinuteOfDay` | 存整数不存时间戳；越界拉回 |
| 任务 | `QuestTable` / `QuestLedger` / `QuestRuntime` | `quests.json`(10) | 状态机 + 前置条件；`RefreshAvailability` |
| 对白 | `DialogueTable` / `DialogueTree` / `MemoryTier` | `dialogues.json`(41) | 4 阶记忆回响；断点可续（`DialogueState`） |
| NPC | `NpcTable` / `NpcLedger` / `NpcScheduleTable` | `npcs.json`(6) + `npc-schedules.json`(5) | 关系/记忆/目标；作息驱动在场与黑市 |
| 线索 | `ClueTable` / `ClueLedger` | `clues.json`(4) | 未读计数；可见性条件 |
| 章节 | `ChapterTable` / `ChapterLedger` | `chapters.json`(9) | 段结算与轴进度 |
| 物品 | `ItemTable` / `InventoryRules` / `BagService` | `items.json`(33) | 堆叠上限；剧情物品不可丢（`PlotItemRules`） |
| 交易 | `MerchantTable` / `MerchantLedger` / `Trade` | `merchants.json`(5) | **价格单一真源 = 声望阶梯**（ADR-032），交情不进价格 |
| 手艺 | `RecipeTable` / `Crafting` | `recipes.json`(2) | 熟练度=次数函数；`DoubleChanceFor` |
| 气运 | `KarmaTable` / `KarmaTracker` / `KarmaTriggers` | `karma.json`(25) | 只记事实不记分数；事件→触发的映射集中 |
| 战斗 | `CombatRules` / `CombatActorState` / `EnemyProfileTable` / `EnemyAi` | `enemies.json`(3) | 部位打击、看破反制、精力口径 8/20/12（D-06） |
| 装备 | `CombatGear` / `CombatEquipmentService` / `GearLedger` | `items.json` + schema 11 | 只存槽与耐久，属性实算；耐久损耗可修 |

### 9.3 **本项目最高频的系统性缺陷：「能力存在 ≠ 功能存在」**

历史上反复出现"系统写完了、单测绿了，但没有任何运行期调用点"：

| 案例 | 现象 | 债务 |
|---|---|---|
| `QuestLedger` 零运行期调用 | 卷一玩不通 | T083 |
| 世界页主角是胶囊体 | 预览页纸偶与镇上自己不是同一个东西 | T091 |
| `radius` 只被静态校验器读 | 地块碰撞没接线 | T038 |
| 气运记账没有生产者 | 行善簿永远空 | T043 |
| 战斗页没有一张真图 | 画面不成立而断言全绿 | T055 |
| `FrontEndController` 订阅的事件从不 raise | CS0067 + 交互断线 | T021（已闭） |

**根治建议**：建立一张**运行期接线矩阵**（系统 → 运行期调用点 → 玩家可达入口 → 断言），并把它做成门禁。
"没有运行期调用点的系统"必须在矩阵里显式标为**库（library）**，不能算功能。
详见任务书 T-05。

### 10.1 三层门禁

### 10.2 证据协议（ADR-035「真图取证」）

1. UI/世界类批处理**一律不带 `-nographics`**（带了会出同 md5 假图，T055）。
2. **退出码 0 不算通过**，只认日志里的 `suite finished, 0 problem(s)`。
3. 同批截图 md5 必须互不相同；判据要按**相位**不按文件全体（同一帧两个出口可以同 md5）。
4. **副本树自证（D-53）**：跑之前交两样——① 树身份 sha；② 覆盖清单逐件来历（OWNED 写域 + overlay_guard）；
   判归属看 mtime 不看文件名。
5. 收工件：报告 + 图 + 命令原文（含退出码）+ sha。

### 10.3 架构风险：**副本树机制是结构性薄弱点**

`Tools/batch-verify-{M,N,O}.sh` 用 robocopy 把工作树的改动搬进副本树，再在副本里跑 Unity。历史事故链：

- **T114**：robocopy 的目录条目"搬 0 个文件"，导致"副本树 0 problem"里根本没带上被测改动；
- **D-53 / T065 / Q1.7**：跑绿的树不是 HEAD 那棵树；"锚点全清"是在混合树上成立的。

D-53 加的自证（sha + 覆盖清单）是**正确的止血**，但根因还在：**用文件复制来构造被测树**。
**建议的根治**：改为 `git worktree add` / `git archive` 导出**纯 HEAD**，再用**显式 overlay 清单**逐件覆盖，
覆盖前后逐件核 md5。这样"副本 = HEAD + 声明覆盖"成为机器事实，而不是脚本约定。见任务书 T-04。

## 13. 扩展手册（"怎么加一个新 X"）

> 这一节是给**不熟悉本项目的 AI 会话**用的：照做即可，不要自己发明流程。

### 13.1 加一个新道具

1. `Resources/Config/items.json` → `items` 增一条（`id` 必须与跨线契约表一致，且全仓唯一）。
2. 若是装备：在 `CombatGear.GearCatalog` 的映射里登记槽位；`items.json` 的 `tier/category` 走已有枚举。
3. 若可买卖：在对应 `merchants.json` 的 `stock` 里挂上。
4. 若可制作：在 `recipes.json` 加配方。
5. 跑 `SaveChecks`（`InventoryChecks` / `InventoryEconomyChecks` / `TradeChecks`）。
6. 需要图标：`make-item-icons.py` / `generate-prop-art.py`，产物进 `Resources/Art/`，跑 `ArtImportGuard`。

### 13.2 加一个新 NPC

1. `npcs.json` 增一条（id、名字、性情、目标、art 路径）。
2. `npc-schedules.json` 增一条（在场窗口 / 交易窗口 / 黑市窗口）。
3. `town-map.json` 的 `npcs` 里放坐标（**只能通过 `make-world-greybox.py` + sync 派生，禁止手改**）。
4. `dialogues.json` 增节点（`DialogueTree.EntryNodeFor(npcId)`）。
5. 跑 `NpcChecks` / `ScheduleChecks` / `DialogueChecks` / `check-town-config-consistency.py`。

### 13.3 加一个新任务

1. `quests.json` 增一条（目标、奖励、前置）。
2. 奖励物品必须在 `items.json` 里存在（`QuestTable.CrossCheck` 会核）。
3. 触发点接到对白/事件（`DialogueTree.AcceptQuestOf` / `KarmaTriggers` / 事件点）。

### 13.4 加一个新敌人

1. `enemies.json` 增一条（部位、掉落、栖息地、AI profile）。
2. 掉落物品必须在 `items.json` 里存在（`EnemyProfileTable.CrossCheckDrops` 会核）。
3. `town-map.json` 的 `encounters` 增一条并指向该敌人（同样只能走生成器 + sync）。
4. 跑 `EnemyChecks` / `CombatChecks` / `CombatEngineShot`。
5. **可达性门禁**：遭遇点必须在可站立地面上（`check-world-mask.py` 的 anchor clearance）。

### 13.5 加一张新材质

1. `world-material-gen.json` 的 `materials` / `generators` 增条目。
2. `terrain-types.json` 的 `types` 增映射。
3. 生成：`make-procedural-base.py` → `compose-final-material.py`。
4. 门禁：`check-world-materials.py`（seam + 内容探针 + finalPass，**不接受数值代替人眼**）。
5. 重跑 `compose-world-chunks.py` + `check-world-seams.py --full-grid`。
6. 大范围观感类改动**必须出对照图交用户**（T019 的教训）。

### 13.6 加一个新页面

1. 新建 `FrontEnd<Page>.cs`，声明 `public sealed partial class FrontEndController`（当前约定）。
2. 在 `BeginPage("<name>")` 里建页；在 `Update()` 里挂键盘分支；`Esc` 回退链里加一级。
3. 加一个 `Assets/Editor/<Page>Shot.cs` 夹具，**至少**覆盖：进入、主交互、退出、边界态。
4. 六关口径下必须能跑出 `0 problem(s)`。
5. **长期建议**：新页面不要再往 `FrontEndController` 里加，改走"独立 MonoBehaviour + 路由注册"（见 §3.3）。

### 13.7 改存档结构（最高危，必须走单批）

1. **先量预算**：当前 payload 实测大小 vs 256KB 上限（W4-A）。
2. 同批改：`SaveModels.cs`（字段 + `Migrate` + `IsValid`）、`SaveRepository.IsValid` 分支、
   `ClientSchema.SUPPORTED_SCHEMA`、`Database/SQL/V1__*.sql`（若涉及表）、`API.md` 的版本字面量。
3. 加 schema-N 历史夹具（`Tools/SaveChecks/schemaN-*.json`）。
4. 跑 `SaveChecks`（含迁移往返）+ `NetworkShot` + `mvnw test`。
5. **回滚必须逐文件 revert**，不许整笔 revert（历史事故 D-41：升版笔与文档笔被裸 commit 捆在一起）。

## 17. 打磨轮目标架构（HD-2D / 八方旅人向）

### 17.1 当前底座判决（2026-10-06 实测，硬证据）

| 项 | 实测 | 后果 |
|---|---|---|
| 渲染管线 | Built-in（`Packages/manifest.json` 无 URP；`ProjectSettings` 无 URP 资产） | 无法用 2D Renderer / Light 2D / Shadow Caster 2D / Shader Graph / URP Volume 后处理 |

## 18. 门禁可信度轮（2026-10-31 ～ 11-01）

> 起因：用户连续三次否掉成果——"感觉不像是一个青石镇，很差劲"、"人物行走每帧形象都不一致"、
> "行走的时候出现留白色块"。三项都不是新功能缺失，而是**已有断言与已有素材同时失真**。
> 本节记录这一轮的**根因、修法与不可再犯的规则**。

### 18.1 五个根因（全部有实测证据）

| # | 症状（用户原话） | 根因 | 证据 |
|---|---|---|---|
| 1 | 地图门禁全绿但镇子不像镇 | `check-town-overlap.py` 读 `town-map.json` 的 `props`/`walkable`，**两个都是空数组** ⇒ 空输入假绿（F-01） | 改读 `building-plots.json` 后立刻报 144 项真实违规 |
| 2 | 镇子不像镇 | **骨架错**：河在镇北缘（y∈[2459,2922]），主街垂直于河，**全城没有一条沿河的街**。真实江南市镇是"一河两街" | `Tools/logs/dispatch/river-street-skeleton.md` |
| 3 | 镇子不像镇 | **素材画错朝代**：25 份里 8 份是清代/景区风貌（白石牌坊、白粉墙、正红灯笼、清式雕花） | `Tools/logs/dispatch/town-props-period-plan.md` §2 |
| 4 | 人物行走形象不一致 | **逐帧独立生成** = 8 次重画。帧间调色板交集 farmer-front **0.466** / farmer-back **0.417**（同角色基线 0.62，不同角色 0.29–0.32） | 本节 18.2 |
| 5 | 行走出现留白色块 | ①抠图泛洪只从四边做，**被轮廓包住的白底清不掉**（farmer-side 单帧 2.9 万～3.8 万纯白像素）②merchant/traveller 有**整块不透明米色纸卡**（traveller-side **27.5%**、merchant-side **22.8%**），而 `PuppetActor.MakeFrameImage` 是 `image.texture = frameSheet`，**没有 key 材质** ⇒ 卡片跟着人滑 | `Tools/check-walksheet-cutout.py` |

### 18.2 行走管线：一次出整张，不再逐帧

**旧流程（已废止）**：逐帧调 8 次 → 8 次独立重画 → 身份必然漂。

**新流程（唯一正确做法）**：

```text
  锚点图（identity anchor）
        +  姿势骨架条（8 格 4×2 拼图，摆幅放大、抬脚可见鞋底、交叉过中线、身体起伏）
        │
        ▼
  一次调用出整张 4×2 走帧图          ← 一次渲染 = 身份锁死在同一张图里
        │
        ▼
  切格 → 抠图（四边泛洪 + 清被包住的纸色块 + 边缘去污）
        │
        ▼
  归一化：脚底线对齐 · 身高统一 · 水平居中按躯干（不按 bbox）· 调色板匹配锚点
        │
        ▼
  拼 6528×1088 sheet → 过闸（运动 + 身份 + 抠图）
```

**实测收益**：farmer-front 一致性 0.466 → **0.873**；farmer-back 0.417 → **0.861**；
大块纸底 36 块 → **0**。

**硬规则**：
- 骨架必须**夸张**（摆幅加倍），归一化会把它收回来；骨架不夸张模型就画成原地踏步。
- 提示词必须**逐格写腿部状态**（`cell N: left foot planted, right heel lifted, sole visible`），
  模型对文字的服从度高于参考图。
- 归一化的水平居中**必须按躯干**，按 bbox 会让摆臂带着人左右晃。

### 18.3 抠图判据（`Tools/check-walksheet-cutout.py`）

六条，全部可独立点火：

| 判据 | 定义 | 阈值 |
|---|---|---|
| C1 残留背景块 | 单格内与纸色 (248,240,222) 每通道差 <12 且 alpha>200 的像素数 | >200 px 判红 |
| C2 大块纸底 | 同色连通域面积 >800 px 的个数 | >0 判红 |
| C3 白边光晕 | 半透明边缘平均亮度 − 不透明内部平均亮度 | >40 判红 |
| C4 帧间一致性 | 8 格两两调色板交集（4bit/通道，剔纸色）最小值 | <0.62 判红（`--ref` 跨图 0.50） |
| C5 身高一致 | 8 格 bbox 高变异系数 | >2.0% 判红 |
| C6 碎白边 | 同色、面积 8–800 px 的连通域个数 | >0 判红 |

**注意**：纸色 b=222 < 232，用"接近白色"一刀切会整批漏掉（C1 曾因此低估 50–110 倍）。
**四角取背景色也不可行**——运行时 sheet 四角是 `(0,0,0,0)`，取到的是黑色。

### 18.4 门禁重判（原判据作废，不是放宽阈值）

| 判据 | 原判 | 现判 | 依据 |
|---|---|---|---|
| G-E1 | `2*radius ≥ 0.72W` | 只报 `(collisionDepth-collisionTop)/height` 分布，阈值待定 | `radius` 是**纵向深度**且运行期不消费（`collisionDepth` 99/99 >0），原判维度错配 |
| G-E3 | `y < footY` | 按 ADR-018 用 `artRect`（从 footY 向下）；`artRect ∩ 走廊 > 400 px²` 判红 | 与 G-E2 同口径 |
| G-E4 | 贴路 | **降 INFO**，不参与退出码 | 运行期 `PlaceInWorld` 无 facing 能力（`FrontEndWorld.cs:835`），写 facing JSON 是假修复 |
| G-A6 | `y ≤ footY < top` | 画带相交 `min(footY+h,top) - max(footY,y) > 0` | `footY` 是画带**顶边**不是中心，原判是"把 footY 当点用"的错 |
| 路线公式 | `sin(2πy/P)` | `sin(y/P)` | 生成器与 `world-mask` 用后者；实测 mask 偏差 **2.0 vs 255**。**运行期 C# 没有第三份公式** |

**铁律**：**假绿比红更糟**。判据写错时改判据（并写清旧判据测错了什么），
但**不许为了让红变绿而放宽阈值或删断言**。
