## W2-A（对应 T102）：把 MySQL 的 UTC 语义从"写在注释里"变成"启动就证明"

问题本质：`DATETIME` 列**不做时区转换**，Connector/J 默认按**连接时区**解释它。
所以 `Instant` 写进 `DATETIME(6)`，存进去的到底是 UTC 墙上时间还是 +08:00 墙上时间，
**取决于运维有没有在连接串里填对参数**——填错了没人知道，而且历史行会整体平移一个时区差，
"谁更新"的判断又会错（这正是第一工单修的那个 bug 的存储层版本）。
H2 测试档永远发现不了：H2 自动建表是 TIMESTAMP，而且测试根本不经过 MySQL 驱动。

要做三件事：

1. **把要求写成硬性**：在 `application-mysql.yml` 里让连接串必须显式带 `connectionTimeZone=UTC`，
   并且**不要只写注释**——加一段启动期校验（见第 3 点）。手册里 `serverTimezone` 全部换成
   `connectionTimeZone=UTC`，并加一句说明它是 `serverTimezone` 的现名。
2. **修 `V1__user_cloud_save.sql` 的失真注释**（`:42-43`）：按 `Instant` 的真实语义重写，
   并明确写出"本表 `DATETIME(6)` 列存的是 UTC 墙上时间，前提是连接串带 `connectionTimeZone=UTC`"。
   V1 从未在任何真库执行过，所以**改注释是允许的**；但**不许改列类型、不许新增迁移脚本**。
3. **启动自检（本工单的核心）**：写一个 Spring 组件（建议放 `com.twelvejade.server.common`），
   在 mysql profile 激活时执行一次"写→读回→比对"：
   - 取一个已知的 `Instant`（例如 `Instant.now()` 截到微秒），通过一个临时实体或 `JdbcTemplate`
     写入一个可清理的位置，再读回来，断言逐字相等；
   - 不相等（说明驱动按非 UTC 解释了）**就直接 fail-fast**：抛异常阻止启动，
     错误信息里写清"检测到连接时区不是 UTC，请在 `TWELVEJADE_DB_URL` 中加 `connectionTimeZone=UTC`"；
   - H2/默认 profile 下这个自检必须**自动跳过**（不能把开发环境搞崩）；
   - 必须有测试覆盖"自检逻辑本身"（可以用假的读回值模拟不一致，断言它抛异常）。

   为什么非要 fail-fast：`ddl-auto: validate` **只比列类型，看不见时区语义**。
   类型对不等于语义对，这层只能自己证明。

## W2-B（对应 T035 的服务端侧）：存档上传路径的健壮性——**允许只暴露问题不修**

现在服务端对上传的存档 payload 只做两件事：查 `schemaVersion` 是否支持、查体积 ≤256KB。
请**用测试**把下面这些现状钉出来，逐条回答"实际行为是什么"：

1. 同一个 `(user, slot)` 被两个请求**并发**上传，最终库里是哪一份？有没有丢中间态、
   有没有可能写出半条记录？（现在是 INSERT-or-UPDATE，没有乐观锁/版本号）
2. payload 不是合法 JSON、是 JSON 但不是对象、缺 `schemaVersion`、`schemaVersion` 是字符串
   ——分别返回什么？是 4xx 还是 500？有没有任何一条路径能把畸形 payload **静默存进去**？
   （静默存进去最糟：读档时崩的是客户端）
3. 错误码与 HTTP 状态是否一致：`code` 字段（0/40102/40903/40904…）与 HTTP status 的对应关系，
   有没有"HTTP 200 但 code 非 0"或"HTTP 4xx 但 body 没有 code"的情况。
4. `updatedAt` 由服务端生成——如果客户端上传的存档里自带一个未来的时间戳，会发生什么？

**处置规则**：
- 纯服务端能安全修的（比如畸形 JSON 应返回 400 而不是 500），直接修，并配测试。
- 需要改**响应契约**或**客户端配合**的（比如加乐观锁、加 version 字段），**不要自己改**，
  写成报告里的"建议方案 + 影响面"，由架构师排期。
- 现状本来就正确的，用测试把它钉住就是有价值的交付。
