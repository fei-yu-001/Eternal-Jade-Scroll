## 3. W4-B｜并发重试的两个盲区（**必做；这是架构师读代码读出来的，不是我抄来的**）

### B-1 现有并发断言弱到检测不到"败者 200 但数据没落库"

`SaveUploadRobustnessTest.concurrentUploadsToSameSlotKeepSingleRow` 现在断的是：
状态 ∈ {200, 409}，且库里恒单行、内容恒为**两份完整 payload 之一**。

问题：**"两份之一"这个判据，在"败者被重试逻辑接住、返回了 200、但那次 UPDATE 实际没写进去"
的情况下同样成立**——因为赢者的那份本来就在库里。也就是说，如果重试路径静默失败，
玩家看到的是"同步成功"，而他的存档其实被丢掉了。这正是我裁定"否决 200 + 幂等语义"时要防的那类
信念破坏（客户端以为自己写成功了），只不过它藏在实现里而不是契约里。

**要做**：把这条用例收紧成**按身份判定**而不是按集合判定：

1. 两份并发 payload 各带一个可区分标记（例如 `{"coins":111,"tag":"A"}` 与 `{"coins":222,"tag":"B"}`）；
2. 记录每个请求各自的 HTTP 状态与它自己那份 payload；
3. 新断言：**凡返回 200 的那个请求，随后 `download` 回来的内容必须逐字等于它自己那份**
   （不是"两份之一"）。败者返回 409 时，则断言库里内容等于**赢者**那份，且响应带 `code:40903`。
4. 跑通它。若这条新断言**是红的**，说明同事务/同 flush 上下文里重试被回滚吞掉了——
   正确修法是把重试放到**新事务**里（`TransactionTemplate` 或 `REQUIRES_NEW` 的辅助方法），
   或者诚实退回 `409/40903` 让客户端重传。**绝对禁止反过来放宽断言来迁就实现。**
   如果它一开始就是绿的，也要把这条更强的断言留在仓库里（它守的是未来的回归）。

### B-2 唯一键冲突兜底 handler 捕获过宽（潜伏缺陷，现在不可经 HTTP 触发）

`SaveController.onDataIntegrityViolation` 对**该控制器内任何** `DataIntegrityViolationException`
一律返回 `409 / 40903「该槽位刚被另一次上传占用，请重试」`。而 B 分支里非唯一类违例是
`throw conflict` 原样上抛的——它会正好落进这个 handler，于是 **NOT NULL / 外键这类真故障
会被报成"客户端可重试的槽位冲突"**：客户端会照提示重试，而重试永远不可能成功，
且服务端一条日志都不会有（全服务只有 1 条 log 调用）。

如实说明现状：按 §1 的 DDL，`payload` 是 `LONGTEXT`、`slot`/`user_id` 在应用层已校验，
**这条路径今天经 HTTP 触发不了**，所以它是潜伏的、不是活 bug。但它是"错误诊断"类的坑，
修它只要几行，而且顺手能把你 W3 报告里"待排期 #1（50001 没有生产者）"闭环掉。

**要做**：

1. handler 内部按 `isUniqueSlotConflict(ex)` 分流：
   - `true` → 维持 `409 / 40903`（现语义不变）；
   - `false` → `500 / 50001` 信封（`ApiCode.INTERNAL_ERROR` 由此第一次获得真实生产者），
     并打**一条 WARN 日志**：异常类名 + 请求路径即可，
     **不得包含 payload / token / password 字样**（否则你自己的 `SecurityAuditTest.logCallsDoNotMentionSecrets` 会红）。
2. 在 `ApiContractCoverageTest` 里**删掉** `RESERVED_WITHOUT_PRODUCER` 对 `INTERNAL_ERROR(50001)` 的豁免条目
   （你在注释里写明"豁免不是永久席"，现在就是兑现的时候），并让方向 A/B/C 三向继续绿。
3. 补一条测试：直接构造一个非唯一类 DIVE（例如 `SaveController.isUniqueSlotConflict` 判 false 的样例）
   送进 handler，断言它得到的是 `500/50001` 而**不是** `409/40903`。
4. `docs/API.md` 与 `README.md` 的错误码表同步（50001 从"预留"改为实际语义）。

**允许改**：`GameServer/src/main/java/**`（限 `save/SaveController.java` 与本块相关行）、
`GameServer/src/test/java/**`、`GameServer/docs/API.md`、`GameServer/README.md`。

## 8. W4-G｜"服务端只存不读"要用机器钉住（为 schema 11 升版铺路）

`payload` 列注释写着"客户端存档 JSON 原文，服务端**只存不读**"。这句话现在是**注释，不是能力**。
升版最怕的就是服务端某个地方偷偷依赖了 payload 内部的某个字段——那样老存档会在新客户端下静默变形。

**要做**：

1. 建 `GameServer/src/test/resources/saves/` 历史存档夹具矩阵：至少 4 份不同形状的 payload
   （最小形状、含数组/嵌套、含中文与 emoji、含 `null` 字段与超长字符串），
   用**文件名标注它模拟的历史 schema 形状**；
2. 一条参数化测试：逐份 `upload` → `download` 取回，断言**逐字往返无损**
   （字节级相等，不是 JSON 语义相等——语义相等会放过键序/转义/Unicode 归一化的漂移）；
3. 一条断言：服务端源码里**不得出现**对 payload 内容的解析分支
   （扫描 `readTree(` / `readValue(` 作用在 payload 上的地方；`SaveController` 只做大小校验的
   那处按显式豁免登记，理由写清）；
4. **（前提已更新，2026-10-06）**：我写这条时两边都还是 10，**现在客户端与服务端都已升到 11**，
   所以原来那个"11 打 10 会怎样"的问题已经不存在了。改成测这三件事，它们决定**回滚安不安全**：
   - 声明 `schemaVersion = 10` 的存档上传到新服务端 → 期望 `200` 且回执 `migratable: true`，
     随后 `download` 内容逐字不变（**老客户端连新服务端不能静默改数据**）；
   - 声明 `schemaVersion = 12`（高于本服务端 11）→ 期望 `409 / 40901`，且**库里不产生任何行**；
   - 用 W4-G 第 1 步那几份历史夹具走一遍"存进去 → 取出来 → 逐字相等"，
     证明升到 11 之后**服务端仍然不读 payload**（这是它敢回滚的前提）。
   结论写进 `docs/API.md` 的一节，标题就叫**「升版与回滚安全性」**：
   架构师要拿它决定"万一把 schema 11 撤掉，玩家存档会不会坏"。

**允许改**：`GameServer/src/test/**`（含新增 resources）、`GameServer/docs/API.md`（部署顺序那一节）。
