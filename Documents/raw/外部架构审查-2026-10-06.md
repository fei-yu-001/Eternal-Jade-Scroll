**这个项目的工程纪律远高于"个人独立开发 + AI 辅助"的平均水平**（有 ADR、有技术债账本、

## 1. 做得好的地方（先讲清楚，避免"只挑毛病"）

1. **验收命令是可执行的、带退出码原文的**。`Tools/run-gates.sh` 聚合 12 道纯逻辑关，
   还带 `--self-check`（防"某道关被静默跳过"）与 `--self-check-strict`。这是很多商业项目都没有的自觉。
2. **"退出码 0 不算通过，只认 `suite finished, 0 problem(s)`"**（T055/T044 的教训）——
   把"假绿"当成一等敌人，方向完全正确。
3. **技术债账本（T001–T123）质量很高**：每条都有"影响 / 当前处理 / 恢复方式 / 防再发"。
   尤其 T018、T026、T032、T033 的"防再发"栏，写的是**下次会怎么再犯**，不是"已修复"。
4. **一条真正深刻的工程原则被反复执行**：*"能算出来的不进存档"*（时间存分钟不存时间戳、
   熟练度存次数不存等级、装备存槽+耐久不存属性）。这直接消除了三类 classic 双真源 bug。
5. **"表会变，玩家已经发生的事不能被表抹掉"**（`IsValidKarma`/`IsValidClues` 不按表判成员）。
   这是产品级的判断，不是技术判断。
6. **缺图不静默**：世界块缺图打 `LogError` + 品红块 + 顶部通知（`FrontEndWorld.BuildWorldChunks`）。
   "没接上"与"世界就长这样"必须可区分——这条做对了。
7. **成本意识**：ADR-002 明确"强结构材质程序化、AI 只出 micro overlay"，避开了 AI 直出平铺材质的坑。
8. **跨端契约有真正的守卫**：`ApiContractCoverageTest` 强制"错误码 = 生产者 = 测试 = 文档"三方一致。
   这是本仓最好的一个测试设计。**下面的 P0-3 正是"这套守卫没覆盖到版本字面量"造成的。**

### P0-1 ｜ 231 笔提交从未离开本机，没有异地备份

**证据**
```text
$ git rev-list --count origin/feature/front-end..HEAD  → 231   （相对 origin/main 是 295）
$ git log --oneline -1 origin/feature/front-end              → 3276436 docs: 阶段一交付记录（灰盒大世界底座）
```

`20_项目状态板.md` 自己写的还是"40+ 笔未 push"，**实际是 231 笔**（相对 origin/feature/front-end；相对 origin/main 是 295 笔）——连这个数字都漂了。

这是唯一一条"出事就不可挽回"的风险。

**建议（不需要用户在场也能做）**
1. 立刻 `git bundle create ../ejs-backup-<date>.bundle --all` 到**另一块盘 / 云盘**；
2. `git fsck --full` 确认对象完整；
3. 把 231 笔按主题分成 5–8 批 push（或直接一次 push 分支）；
4. 定一条硬规矩：**每轮关账必须 push 一次**，"等用户点头"不能成为长期状态。

### P0-3 ｜ 契约文档已经漂了：`API.md` 还说"服务端支持 schema 10"

**证据**
```text
GameServer/docs/API.md      :412  "40901 | schemaVersion > 10。实测:{\"code\":40901,\"message\":\"存档版本 99 高于本服务器支持的 10。\"}"
GameServer/docs/API.md      :...  download 样例：{"schemaVersion":10,...}
```

也就是说：**代码已经同批升到 11（做对了），但新会话会读到的契约文档还写着 10。**

**影响**：新会话按 `API.md` 写的测试会与真实服务端相反；比"没文档"更坏（`D-49 口径给错方向比不覆盖更坏`）。

**建议**：把版本字面量纳入已有的三方一致性守卫。
最便宜的做法：在 `ApiContractCoverageTest` 里增加一条断言——
`API.md` 中出现的"支持的 N"与 `ClientSchema.SUPPORTED_SCHEMA` 相等；
或更彻底：`API.md` 的版本行由常量生成。见任务书 T-03。

## 3. P1 —— 结构性问题，应在下一轮之前处理

### P1-1 ｜ 验证树是"复制出来的"，不是 HEAD 本身（R4）

**证据**：`Tools/batch-verify-{M,N,O}.sh` 用 robocopy 把工作树改动搬进 `.batch/*` 副本树再跑 Unity。
历史事故链：
- **T114**：robocopy 目录条目"搬 0 个文件"，`副本树 0 problem` 里根本没带上被测改动
  （3 号 实测 `InventoryEconomyShot` ok 334→375 才知道）；
- **Q1.7 / T065**：跑绿的那棵树不是 HEAD（"锚点全清"在混合树上成立）；
- **D-53**：加"树身份 sha + 覆盖清单逐件来历"是**正确止血**，但根因还在。

**建议（根治）**：`git worktree add --detach <dir> HEAD`（或 `git archive HEAD | tar -x`）导出**纯 HEAD**，
再用**显式 overlay 清单**逐件覆盖；覆盖前后逐件核 md5。
这样"副本 = HEAD + 声明覆盖"变成机器事实，而不是脚本约定。见任务书 T-04。

### P1-2 ｜ 「能力存在 ≠ 功能存在」反复发生（R5）

**证据**（全部是项目自己登记的）：

| 案例 | 债务 | 状态 |
|---|---|---|
| `QuestLedger` 零运行期调用 ⇒ 卷一玩不通 | T083 | 高危 |
| 世界页主角是深绿胶囊（预览页却是真纸偶） | T091 | 高危 |
| 地块 `radius` 只被静态校验器读，运行期碰撞没接线 | T038 | 已派 M |
| 气运记账没有生产者 ⇒ 善行簿永远空 | T043 | 已派 O |
| 战斗页 11 张图全 38664 字节同一 md5 | T055 | 已证成，根因 `-nographics` |
| `FrontEndController` 订阅的事件从不 raise | T021 | 已闭 |

**这不是偶发 bug，是流程缺口**：项目有"系统完成"的判据（门禁绿），但没有"功能可用"的判据
（运行期调用点 + 玩家可达入口）。

**建议**：建立**运行期接线矩阵**（系统 → 运行期调用点 → 玩家可达入口 → 断言），
并把它做成门禁：新系统若没有运行期调用点，必须在矩阵里显式标为"库（library）"。
见任务书 T-05。

### P1-3 ｜ 夹具层（11,185 行）没有架构管理，`ForCheck` 钩子长在生产类里（R7）

**证据**
```text
Assets/Scripts（生产）    ~17,332 行
Assets/Editor（Unity 夹具）~8,105 行
Tools/SaveChecks（离线夹具）~3,080 行
ForCheck 钩子分布：FrontEndTrade 25 · WorldPropLayer 13 · FrontEndCombat 11 · PuppetActor 10 · FrontEndWorld 7
```
夹具代码已达生产代码的 64%；生产类里直接放取证方法（`LoadMerchantFixtureForCheck`、
`CombatSetFoeFallbackForCheck`、`LoadPlotsFromTextForCheck`、`CombatCycleLockedPartForCheck`…）。

**影响**：① 生产构建携带取证代码；② 夹具改动的 diff 混进生产文件的历史；
③ 夹具 bug 会伪装成产品 bug（D-21 的 `NpcDialogueShot` 5 条红是**夹具口径错**，不是缺美术）。

**建议**：把 `*ForCheck` 收进 `#if UNITY_EDITOR` 或独立 `partial` 文件；为夹具层建一张"谁负责哪个 Shot"的表。

### P1-4 ｜ 没有 CI，231 笔提交从未被任何自动化检查过（R8）

所有门禁都是"人工在会话里跑，然后把输出粘贴进文档"。这在**没有 CI** 的前提下是唯一的做法，
但它的代价是：没有人在无人值守时看过这 231 笔提交。

**建议**：加最小 GitHub Actions（**不需要 Unity**）：
`mvnw test` + `dotnet build UnityCompileChecks --no-incremental` + `run-gates.sh --self-check`
（纯逻辑 12 关依赖 Python+numpy+PIL，CI 上可装）。Unity 六关继续人工/夜间。
见任务书 T-08。

### P1-5 ｜ 存档容量预算未实测，256KB 上限是硬墙（R9）

`maxPayloadBytes = 262144` 三处口径一致（客户端配置 / 服务端应用层 / Tomcat）。
但 schema 11 之后**没人量过实际存档有多大**。W4-A 正在办这件（"存档体积实测与 256KB 余量"）。
在实测数据出来之前，**任何给 `SaveData` 加字段的动作都应该暂停**。

### P1-6 ｜ 真 MySQL 从未验证（R10）

- `Database/SQL/V1__user_cloud_save.sql` 没在真 MySQL 8 上执行过（T024，转用户待办）；
- H2 与 MySQL 在类型/方言/并发唯一键上的差异可能集中爆雷；
- `MysqlUtcSemanticsCheck` 已写好但需要真库。

**建议**：`GameServer/scripts/docker-compose.mysql.yml` + `verify-mysql.ps1` 已经备好——
缺的只是"真的跑一次"。这是**执行问题，不是设计问题**。
