## 2. W3-A｜并发上传：服务端重试 + 409/40903（**优先级最高，先做这块**）

**现状**（你上一轮实测）：两个并发请求同时上传同一 `(user, slot)`，都走 `orElseGet` 的"空槽"分支各自
INSERT，败者撞 `uk_saves_user_slot` 抛 `DataIntegrityViolationException`，客户端收到 **HTTP 500 +
Spring 默认 error JSON（body 里没有业务 code）**。库里数据是对的（单行、两份完整 payload 之一、无半条），
**但玩家看到的是"服务器坏了"**。

**要做**：

1. 在 `SaveController` 的上传路径上加**一次有界重试**：捕获唯一键冲突后，
   重新 `findByUser_IdAndSlot` 取到已存在的那一行，走 UPDATE 分支再存一次。
   重试**只一次**，不要写成循环（循环会掩盖真正的故障，也会让慢查询堆积）。
2. 重试仍失败（或重试路径抛出非冲突类异常）才返回 **HTTP 409 + 业务码 40903**（"槽位冲突"，
   这个码在 `ApiCode.java` 里已预留但当前无生产者，语义正好）。响应体必须沿用既有信封
   （`{"code":..,"message":..,"data":..}`），**不许出现"4xx 但 body 没有 code"**。
3. 加 `@ExceptionHandler(DataIntegrityViolationException.class)` 兜住这条路径，
   确保任何唯一键冲突都不会漏成 500。
4. **测试**（在你上一轮的 `SaveUploadRobustnessTest` 上扩，不要新建重复类）：
   - 并发用例断言改成：**败者不再拿到 500**，只允许 `200`（重试成功）或 `409/40903`；
   - 断言重试成功后库里仍是单行、且内容是两份完整 payload 之一（不变量不许松）；
   - 加一条"非冲突类的 DataIntegrityViolation（例如 payload 为 null 触发 NOT NULL）
     必须仍然报错、不许被重试逻辑吞掉"的用例——**这是重试最容易犯的错：把真故障也重试成静默**；
   - 断言 40903 的响应体里有业务 code。
5. 在 `GameServer/README.md` 的上传契约表里补 409/40903 这一行，并写明客户端应如何处置
   （提示"该槽位刚被另一次上传占用，请重试"，**不许静默失败**）。
   客户端侧的处理**你不要写**——那是另一条线的活，你只负责把契约和文档交清楚。

**允许改**：`GameServer/src/main/java/com/twelvejade/server/save/**`、
`GameServer/src/test/java/com/twelvejade/server/SaveUploadRobustnessTest.java`、`GameServer/README.md`。

   参考 `SaveTimestampTest` 已有的写法），断言逐字相等而不是"大于等于"。
4. 新增一条**护栏测试**：扫描 `src/main/java` 源码文本，若再出现裸 `LocalDateTime.now()` /
   `Instant.now()`（`TimeConfig` 自身除外）就让测试失败——把这条纪律从"注释里写着"变成"机器守着"。

**允许改**：`GameServer/src/main/java/**`（仅时钟取值方式）、`GameServer/src/test/java/**`。

## 6.8 W3-I｜数据库约束核对 + 性能基线

**两块都很小，但都是"没人做过所以没人知道"的那类。**

1. **约束与索引核对**（`GameServer/scripts/verify-schema.sql` 或并入 W3-B 的脚本）：
   从 `information_schema` 打印 `users` / `saves` 两表的列类型、可空性、默认值、全部索引与唯一约束，
   与 `Database/SQL/V1__user_cloud_save.sql` 逐条对照，**任何不一致都要列出**。
   重点确认：`saves uk_saves_user_slot` 真的存在（W3-A 的重试逻辑依赖它抛冲突）；
   `users.username` 有没有唯一索引（没有的话并发注册能造出两个同名账号）；
   按 `token_at` / `created_at` 的查询有没有可用索引。
2. **性能基线**（`GameServer/docs/PERFORMANCE.md`）：本机实测并记录
   注册 / 登录 / 上传（三档存档尺寸，用 W3-F 的结果）/ 下载 / 列表 的 p50 与 p95 延迟，
   以及 BCrypt 单次哈希耗时（与 W3-D 第 3 项同一测量，别做两遍）。
   **只要真实数字和一句结论，不要优化任何代码**——这个项目是单机自用，
   基线的价值在于"以后变慢了能看出来"，不在于跑分。

**允许改**：`GameServer/scripts/**`、`GameServer/docs/**`（均新增）。

## 6.9 W3-J｜message 文本耦合审计（小，但可能挖出真 bug）

服务端响应里有 `code`（数字）和 `message`（中文文案）。**契约的稳定性应该只建立在 `code` 上**；
如果客户端是靠比对 `message` 字符串来分支的，那改一句文案就是一个破坏性变更。

**要做**：

1. 在 `GameServer` 侧列出所有 `message` 的产生点与它们是否被任何测试**按文本断言**
   （测试里 `hasEntry("message", "…")` 这种）。
2. 在客户端侧**只读检查** `Assets/Scripts/Network/**` 与 `Assets/Editor/NetworkShot.cs`：
   有没有 `if (message == "...")` / `message.Contains("...")` 这类按中文文案分支的代码。
   （**只查不改**——那是另一条线的文件。）
3. 结论写进 `GameServer/docs/CONTRACT.md` 的一节：哪些文案是稳定的、哪些可以随便改、
   客户端有没有违规依赖。发现违规的**列出来交给架构师**，不要自己改客户端。

**允许改**：`GameServer/docs/**`（新增）。

## 6.10 交付节奏（改了：一块一交，不要攒）
